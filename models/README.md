# Отдельные компоненты Simulink: Model Reference

Из таблицы преподавателя **Component Summary** следует, что обычные Virtual / Atomic Subsystem находятся внутри родительской модели; для независимой работы над семью модулями удобнее отдельные файлы компонентов. Мы выбираем **Model Reference**.

## Генерация

В MATLAB с установленным Simulink, из корня проекта:

```matlab
build_component_models
build_simulink_model
run('tests/run_simulink_smoke_tests.m')
```

Будут созданы файлы `models/generated/UAV_Navigation_01.slx`, ..., `UAV_Energy_07.slx`, `UAV_Dynamics_Overview.slx` и верхнеуровневая `UAV_Team_Model.slx`.

**Критическое ограничение:** созданные модели — **заглушки интерфейсов**, проходящие scalar-сигналы через первый вход. Они демонстрируют независимое хранение моделей и связи на верхнем уровне, **не вызывают функции MATLAB**, не моделируют сенсоры, алгоритмы или реальный полёт. Фактическая миссия запускается `run_project`, который вызывает функции из `team/`.

После проверки модели могут поэтапно заменяться полноценными реализациями. Не обозначайте эту схему как законченный исполняемый Simulink-симулятор на защите.

## Совместная работа

- Семь разных файлов `.slx` можно независимо редактировать в Git-ветках участников.
- Генератор **не перезаписывает** существующие файлы моделей, чтобы не стереть изменения участников.
- После проверки в MATLAB зафиксируйте в Git согласованные `.slx`, контракты сигналов и изменения скриптов.
- Исходный MATLAB-код остаётся источником рабочих алгоритмов до переноса логики в Simulink и прохождения системных тестов.

См. `docs/INTERFACES.md` и `docs/REQUIREMENTS_AND_TESTS.md`.
